# Changelog

## Unreleased

- Jobs read the vault with the Read, Grep and Glob tools, never with `ls`, `cat`, `grep` or `head` in the shell: every job prompt says so, and the skills, `CLAUDE.md` and routines name the tools instead of shell commands. morning-triage, debt-review, feedback-digest and weekly-digest were refused when they listed `.claude/adapters/` or read earlier reports from the shell, and feedback-digest wrote no report.
- The cockpit shows the pages of the chosen profiles, not only their names in the Pages table: it embeds each pack's `cockpit_pages` (engineering's pulse and delivery, product's roadmap, a private pack's own), in the order of the packs, and leaves out a page whose report is off, which would stay empty.
- The cockpit shows the short glance pages of the chosen profiles, not only their names in the Pages table: it embeds each pack's `cockpit_pages` (engineering's pulse, a private pack's own), in the order of the packs, and leaves out a page whose report is off, which would stay empty. The delivery, roadmap, developer and content pages, which repeat the cockpit's tables, stay in the Pages table. `cockpit/today.md` no longer has an overdue table, since the cockpit's live list shows it, and the deadlines list shows only deadlines still to come.
- The cockpit no longer shows today's title three times: it embeds `cockpit/today.md` without a heading of its own, and a new vault's Obsidian settings hide the file name above each page (`showInlineTitle: false`), since every page has its own title.
- An update saves a kit file's new version in `.control-tower/updates/` only when the kit changed it. A file you edited, or a page a report or a skill rewrites (`cockpit/today.md`, `cockpit/pulse.md`), is kept without a copy when the kit's version is the one installed: every update no longer leaves a pile of identical copies to merge.
- A job that runs `slackcli` no longer counts as blocked: the known-command table (`adapters/commands.json`) can set environment switches for a command (`env`), written into the settings of the jobs allowed that command, and `slackcli` gets `SLACKCLI_NO_UPDATE_NOTIFIER=1`, so its update check no longer reaches `api.github.com`, which the job's sandbox refuses. Only the kit's table sets an environment; a `commands` answer cannot.
- The Run context also gives Unix times: now, today 00:00 and the previous working day 00:00, local midnights in the installed timezone. A job whose command takes epoch seconds (`slackcli conversations read --oldest`) no longer needs `date`.
- Dated notes start with their date, so a folder of meetings or reports sorts by date in Obsidian: meetings `journal/meetings/<type>/YYYY-MM-DD-<type>.md`, one-to-ones `journal/meetings/1-1/<person>/YYYY-MM-DD-1-1-<person>.md`, reports `journal/reports/YYYY-MM-DD-<kind>.md` (a weekly report takes the Monday of the week it covers), your own reports `journal/reports/YYYY-MM-DD-my-<id>.md`. The vault's `CLAUDE.md` states the rule; a pack report may not be named like your own (`…-my-…`). Notes written before keep their names: they are never renamed, so the first run of a report after this update finds no previous report of its kind to compare with. The reports look for their previous one by its date and kind (`????-??-??-health.md`), never a report of yours.
- Know when to update: "hello control tower" and "check my setup" run the update check and say in one line when a new version of the kit is ready. With automatic reports, the schedule also runs `configure.py update --notify` every Monday at 09:00 (`com.control-tower.kit.update`, an id no job can have): it fetches the kit's origin only when it is an https address, never prompts, changes nothing, and shows "A new version of the control tower is ready. Open Claude on your <vault> folder and say: update the kit." when an update or an unfinished one is waiting and the kit's folder has no developer's changes. The uninstaller removes it with the schedule.
- The vault in your language: when the language is not English, the guided install has Claude translate the visible texts of the vault's templates, dashboards and pages (`install.py --strings` lists them; `translation_file` in the answers brings the translation), checked by `installer/translate.py` (words only: the same links, tokens, tags, handles and code, one line each, no new table cell, heading, quote, list, code, link, HTML or comment). The translation, its vault texts only, is kept in `.control-tower/translation.json` and put back every time the installer writes those files, so updates keep it and nothing looks edited; skills, `CLAUDE.md`, folder names and every heading a skill, rule or report names (`## ✅ Tasks`) stay in English, so they still find their sections. `/control-tower` translates what an update adds and the whole vault after a change of language (`configure.py translate --missing`, then `--file`).
- `/control-tower` in every Claude session: after a yes in the guided install (or `configure.py set --everywhere on`), the installer writes one personal skill (`~/.claude/skills/control-tower`, or under `CLAUDE_CONFIG_DIR`) holding the kit's own hub as is (never the vault's copy, a pack's or an answer's text: a synced vault or pack is not trusted in every session; when a pack changes the hub, it is not written), with the vault it serves; in another control tower vault's session it gives way to that vault's own. Its path and checksum are recorded in the runtime's `install.json`: a skill of the user's, an edited copy or another install's is never replaced or removed. It goes when turned off and with the runtime at uninstall, and kit updates refresh it. Signing in to a tool still happens in the vault session. A vault or runtime path with a backtick, a control character or `-->` is refused.
- Your own tool for a capability: `"tools": {"<capability>": "connection:<id>"}` lets the kit's reports that need a capability (logs, for example) use one of your connections to an MCP server or a command instead of a kit tool. They get its read tools and its server, and read `.claude/adapters/<capability>-guide.md`, a guide `/control-tower` writes with you from what you already have ("Use one of your connections for a capability"). `configure.py set --tool <capability>=connection:<id>` applies it with consent; the doctor warns while the guide is missing; a cloud routine never counts on it.
- What a second real install showed: the tool question is a list to tick again (pages of at most four, all on one screen, nothing ticked, "Other" for any tool not listed), since typing every tool was slow; the language question says plainly that the vault's structure stays in English; at the end, Claude offers to open the vault session itself when the app can, and points any control tower command asked in the install session there.
- The README has two parts: using Control Tower (install in one sentence, the three folders it creates, opening the vault in Obsidian step by step, what to say in the vault session, what it promises), and developing the kit (terminal install, layout, how it works, tests). The install skill guides "Open folder as vault" in Obsidian step by step: Obsidian does not open an unknown folder as a vault by itself.
- The vault's language: notes and reports are written in the language of the answers' new `language` (default `English`; a name in letters, since it goes into every job prompt). The guided install asks it first and continues in it; `configure.py set --language` changes it later. What a first real install showed is fixed: the summary is also in the confirmation question itself (the user may see only the question), the tool question is a plain message with no suggested lists, profiles show their names, temporary files are deleted one by one, and "aws logs" / "log aws" name CloudWatch. Uninstalling no longer says the routines the kit offered still run on claude.ai: it says to delete those the user created, if any.
- Install from one pasted sentence and four questions. The README starts with the sentence to paste in the Claude desktop app's Code tab; the install skill asks which describes your work, which tools you use (one free-text answer), where the vault goes and whether reports run automatically, then shows one summary whose yes is also the consent to what each report reads, installs, checks, offers Obsidian and the cloud routines, and ends by sending you to a new session on the vault ("hello control tower"). `install.py --match-tools "<text>" --packs <ids>` (in `installer/toolnames.py`) maps the tools named to adapters per capability (the adapter id or one of the manifest's new optional `aliases`, whole words, any case, the longest name first), sets every capability not named to `none`, leaves out a tool named after a negation ("not Jira", "pas de Jira"), and returns conflicts and unknown names; `--match-tools-file` reads the answer from a file, so what a user typed never goes on a command line, and `--known-tools --packs <ids>` lists the tools those packs can use. A vault folder that is the root, the home folder or above it, or that holds the kit or the runtime, is refused: reports read the whole vault. Name, handle and timezone come from the computer (the account's full name, the first name without accents as the handle, the system timezone) when the answers leave them out, and the dry run reports them as `owner`. The vault's `CLAUDE.md` runs `/control-tower` on "hello control tower". The terminal wizard (`--interactive`) is removed: it now points to the guided install. getting-started has one path, plus answers files for developers. The schedule code moved from `install.py` to `installer/scheduling.py`.
- Uninstall from the vault: `/control-tower` asks "What do you want to remove?" (stop the automatic reports only, or remove the kit and keep all notes), then separately whether to remove the tool connections it added and whether to delete the kit's own folder, shows one dry run of everything in plain words, and removes after one "Remove now?". `uninstall.py --schedule-only` unloads the schedule and keeps everything else; `--remove-connections` runs `claude mcp remove --scope project` from the vault only for the servers in `connections_added` whose entry is unchanged since they were added; `--remove-kit` removes the kit's folder last, with the runtime, listed in the dry run, and refuses unless its origin holds everything in it after a `fetch --prune` (no edited, untracked or ignored file but build output, no commit of HEAD or of any branch or tag the origin lacks, no stash, other worktree, rebase or merge in progress), it holds neither the vault nor the runtime, and no other vault installed from it runs automatically (its `/control-tower` could no longer stop it). Both need `--vault`. The uninstaller now ignores a manifest path outside the vault, and a damaged `answers.json`, `.mcp.json` or `manifest.json` only skips what it describes.
- Update the kit from the vault: `configure.py update` fetches the kit's origin and says how many versions behind it is, a developer's changes (edited files, local commits), what the CHANGELOG adds, the version it would move to and whether an update is pending; `--apply --to <version>` refuses over a developer's changes or an untracked file the move would overwrite, fast-forwards the kit's folder to exactly that version, then hands over to the new version's `configure.py refresh`, an ordinary change: new access needs a yes, edited files are kept, the schedule is loaded again only if it was, the runtime keeps its `claude`. When the refresh is refused before it writes anything (new access waiting for a yes), the kit's folder goes back to the commit it was on; a refresh that fails after writing leaves it on the new version, shown as pending. It lists the kept files and the cloud routines whose prompt changed. The installer records the kit commit it installed, once everything else is written (`kit_commit` in the runtime's `install.json`), so a kit moved without being installed shows as pending. A malformed `answers.json` is refused with a reason instead of a traceback. `/control-tower` asks before updating and offers to merge the kit's new parts into each kept file.
- Fixing a blocked job: `configure.py denials` gives each refusal its `connection` (MCP server, command or site) and `expected` (true only when the job declares that connection: its own rules, its tools' adapters, the sources of a report of your own; a command only in the group it declares, `gh pr` but not `gh api`; never a later grant), and a `runs` list with each job's latest outcome (ok, refused, auth, server, timeout, network, failed). The runner reads Claude Code's stream-json output and writes, per job, the run's outcome, the connections that did not start and the hosts the sandbox blocked, read only from a failed command's closing sandbox block (`logs/<job>.run.json`); the real-CLI facts script uses the same parser. `/job-permissions` asks once per connection, flags unusual refusals with "Not now" recommended, grants an "Allow anyway" as that one rule only (`show` and "check my setup" list, as `unexpected_grants`, every granted rule outside the connections its job declares), and explains sign-in, timeout and blocked-address failures. Guard refusals, which Claude Code reports as error tool results under stream-json (runtime fact F10), are labeled as the guard's by the id of the refused call. Runtime facts F8b, F9 (`${NAME}` filled in `--mcp-config`), F10 and F11 (a server that needs a sign-in shows as `needs-auth`, and the run still succeeds without it) are checked by the facts script. The notification fires when a job is refused something, fails, runs out of time, could not reach a tool it must sign in to again, or one of its connections did not start (it names the server, since such a run does not fail), and says: "Open Claude on your <vault> folder and say: fix my job."
- `/control-tower` can automate a report: it asks what the report should do and where its data comes from, writes the skill in the vault (checked with `check-skill`), offers to try it, asks when it should run, schedules it with `add-job` after showing what it will use, runs it once and hands any refusal to `/job-permissions`, or creates its routine when it runs on claude.ai. "Automate a report" is in the first question; connecting a tool offers to make a report with it.
- A report of your own can run on claude.ai as a cloud routine (`add-job --runs-on cloud`, `"runs_on": "cloud"`): the installer renders it from the same skill-job prompt into `routines/my--<id>.prompt.md` and `routines.json` with its connectors, and schedules nothing on this computer; the routine is created by the user like a pack routine. claude.ai connectors (Gmail) become sources of cloud reports (`add-connection --connector`); a report on this computer cannot use one, and a cloud report cannot use the vault's MCP servers or commands. `uninstall.py` lists the routines to delete on claude.ai. A cloud routine commits only its own report. The runner now refuses to start any job while the vault's `.claude/settings.json` would widen it (rules, hooks, env, MCP servers), and the doctor fails: such a file could come from a synced vault or a routine.
- Schedule any skill of the vault as a report of your own: `configure.py add-job` / `remove-job` record `my_jobs` (`{id: {skill, uses}}`; its days and time in `jobs.<id>`, like any job), and the installer renders it from one generic prompt (`core/jobs/skill-job/prompt.md.tmpl`) that reads the skill with `Read`, takes its dates from the Run context and writes `journal/reports/my-<id>-YYYY-MM-DD.md`. Its sources (`uses`) are known tools and connections; it gets their read tools and nothing else, and a connection's server starts only for the reports that use it. `configure.py check-skill` checks the skill like a pack skill (closed frontmatter, no `allowed-tools`, dates from the Run context); `set --job <id> --uses` changes the sources; a connection a report uses cannot be removed, and a connection id may not be a capability name. The doctor warns when a report's skill is missing. Your reports write `journal/reports/my-<id>-...`, a name no pack report may use. Any change that adds a scheduled run (a report, a pack, a job turned back on) now needs the user's yes like any other new access.
- Connect a tool the kit does not know, by answering questions in `/control-tower`: an MCP address (`configure.py add-server` adds an https address on a public host, with nothing secret in it, to the vault's `.mcp.json` with `claude mcp add`, never a shell) or a command-line tool (its web addresses known or recorded first), with the read tools reports may use (a command's rules end with a read word: `gh pr list`, never the group `gh pr`; an address whose path or subdomain holds a long code is for a developer). `configure.py add-connection` / `remove-connection` record `connections` in the answers (`{id: {server or command, read_tools}}`), every tool checked like a grant; `show` and `choices --kind connections` list them. A connection's server is approved and fingerprinted like a known tool's, and no report uses a connection until it is chosen as a source of one of the user's own reports.
- Connect a known tool by answering questions: `/control-tower` adds it to the vault's `.mcp.json` (the servers scheduled reports can see), has you sign in, records the server name reports really see (`configure.py connect`, `servers` in the answers) so the adapter's rules follow it, and lets you choose the read tools of an adapter that ships none (`configure.py set-permissions`). Each job gets its own `mcp.json` with a copy of the connected servers it calls, and the runner passes it with `--strict-mcp-config`, so a job starts no other server; a server whose `.mcp.json` entry changed since it was connected (a fingerprint) is dropped at the next change of setup and the doctor fails; jobs cannot read `.mcp.json`; the doctor flags `.mcp.json` servers no report is connected to. Adapter install commands add servers to the vault (`--scope project`) and keep keys as quoted `${NAME}` references, never their values; tools set up by a developer (keys, client secrets, Sentry's organization address) are finished with "connect" afterwards. Adapters say how they are connected (`connect`: `sign-in` or `developer`). Connecting a new server, or one whose entry changed, is new access that needs a yes. Jobs write only Markdown notes (the guard), so they cannot plant a file a server or a tool would run; Google Analytics runs with `pipx run --spec` for the same reason. Runtime fact F1c (the `--strict-mcp-config` check) is added to the facts script.
- `configure.py probe` runs Claude once the way a job runs and records the MCP servers and tools a job sees (claude.ai connectors are counted, not offered: jobs cannot use them). `configure.py choices` turns any list into questions of at most 4 options ("All N" / "Let me choose" / "None", then pages of 4), and never offers a tool that acts; every skill asks long lists through it (a test checks it). More MCP tool names count as actions and are never granted (call, invoke, insert, put, patch, save, cancel, drop, navigate, click, fill, draft, destructive, sql, start, stop, push, grant, reset...; commit, start, draft, sql and type are nouns after a read verb, as in get_commit), and `choices` recommends only tools whose name starts with a read verb (get, list, search, query...); the CloudWatch adapter no longer allows `cancel_logs_insight_query`. `probe` starts only the `.mcp.json` servers named with `--server`.
- `/control-tower` in the vault: check the setup, change it (profiles, tools, report times, which reports run, automatic runs), fix a blocked job, get a kit file back, by answering questions. `configure.py set --dry-run` shows what a change would do; `configure.py fresh-copy` restores the kit version of a file and keeps yours in `_system/archive/`. No message or doc tells you to edit the answers file any more (a test checks it).
- `installer/configure.py` (was `installer/permissions.py`) is the one door to `answers.json`: `show` (packs, tools, jobs with days, time and state, schedule) and `set` (`--add-pack`, `--remove-pack`, `--tool cap=tool`, `--job id --time/--days/--enabled`, `--schedule on|off`) join `grant`, `revoke`, `add-command`, `remove-command` and `denials` (was `list`). Every change is checked before anything is written, applied by the installer, and rolled back if the installer refuses; a loaded schedule follows the change. A change that gives jobs more access (a job turned back on, a pack or a tool added) is refused until the user has seen that access and said yes (`--accept-access`). Loading the schedule no longer removes the launchd agents of another install (with other job ids).
- Jobs never use the `Skill` tool (denied, and never granted): a skill could bring its own tools. Job prompts already read their skill file with `Read`.
- A command granted to a job reaches, inside the sandbox, the web addresses it needs: from `adapters/commands.json` (`gh`, `twg`, `slackcli`, measured with the real CLI) and from the `commands` answers, which `/job-permissions` records after asking which address an unknown command talks to (`installer/configure.py add-command`). The `gh` exception for macOS certificates comes from that table. Host names are exact and public, never a wildcard, an IP address or a local-only name, for `WebFetch` too; write folders are a tool's own folder under a per-user log or cache root. `remove-command` takes an address back.
- Jobs no longer run `date` or `ls`: `Bash(date)` and `Bash(ls:*)` leave the base rules, the guard loses its `date` argument parser, and generic file readers (`date`, `ls`, `cat`, `head`, `tail`, `grep`, `rg`, `tar`, `open`...) can never be granted, by a pack or by `/job-permissions`. The next update of the kit refreshes the job settings.
- Jobs get their dates from the runner: a `## Run context` block at the top of each prompt (now, today, ISO weeks, previous working day, in the installed timezone). Job prompts no longer run `date`, `weekly-digest` finds notes with Glob instead of `ls`, and the skills jobs follow say to use the Run context first. See docs/scheduling.md.
- `tests/e2e/smoke_real_claude.py --facts` checks the Claude Code behaviours the kit relies on, with the real CLI; results in docs/design/runtime-facts.md. Found with Claude Code 2.1.332: jobs do not see MCP servers added at user scope (docs/adapters.md now says so), and a claude.ai connector's tool is refused in a job even with its exact allow rule.
- Job permissions, secure by default and granted by answering questions: the installer report lists in plain words what each job may use (`permissions_summary`), the guided installer asks once and disables the jobs you refuse, and the new vault skill `/job-permissions` explains each refusal of a job's latest run (`<ct_home>/logs/<job>.denials.json`) and allows what you say yes to (`job_permissions` in the answers, written by `installer/configure.py`, never by hand). See docs/permissions.md.
- Simpler guard and policy: the guard no longer parses shell commands (which commands a job runs is decided by its rules); one list of things never allowed, for packs and users alike. The `trusted_commands`, `trusted_env`, `trusted_mcp_tools` and `trusted_domains` answers are gone (ignored if present). Re-run the installer (`--update`).
- Claude Code's sandbox around every job that may run a command, automatically: writes only in the vault, no read of the secret folders, network only to the hosts the job and its adapters declare (`network`); the job refuses to run where the sandbox is not available. The `strict` answer is no longer needed and is ignored. On Linux the doctor fails when `bwrap` or `socat` is missing.
- Private packs (`pack_dirs` in the answers): packs kept outside the repository, which may replace or exclude core files (templates, rules, language). See docs/private-packs.md.
- Runtime-only installs (`--runtime-only`): runner, guard, jobs and schedule on an existing vault, nothing written in it but `.control-tower/`.
- `install.py --update`: refresh the kit files you never edited, keep the ones you edited (new version saved in `.control-tower/updates/`), leave deleted files deleted. See docs/updating.md.
- Job guard: jobs can read their skills, adapter notes and rules again (they wrote empty reports); glob and grep bypasses closed. Re-run the installer (`--update`) to get the fixed guard.

## 0.1.0 (unreleased)

- Guided installer skill, terminal wizard, answers files, doctor and uninstaller.
- Local scheduled jobs (launchd, cron) with a guard hook; cloud routine prompts.
