# Changelog

## Unreleased

- Fixing a blocked job: `configure.py denials` gives each refusal its `connection` (MCP server, command or site) and `expected` (true only when the job declares that connection: its own rules, its tools' adapters, the sources of a report of your own; a command only in the group it declares, `gh pr` but not `gh api`; never a later grant), and a `runs` list with each job's latest outcome (ok, refused, auth, server, timeout, network, failed). The runner reads Claude Code's stream-json output and writes, per job, the run's outcome, the connections that did not start and the hosts the sandbox blocked, read only from a failed command's closing sandbox block (`logs/<job>.run.json`); the real-CLI facts script uses the same parser. `/job-permissions` asks once per connection, flags unusual refusals with "Not now" recommended, grants an "Allow anyway" as that one rule only (`show` and "check my setup" list, as `unexpected_grants`, every granted rule outside the connections its job declares), and explains sign-in, timeout and blocked-address failures. Guard refusals, which Claude Code reports as error tool results under stream-json (runtime fact F10), are labeled as the guard's by the id of the refused call. Runtime facts F8b, F9 (`${NAME}` filled in `--mcp-config`), F10 and F11 (a server that needs a sign-in shows as `needs-auth`, and the run still succeeds without it) are checked by the facts script. The notification fires when a job is refused something, fails, runs out of time, could not reach a tool it must sign in to again, or one of its connections did not start (it names the server, since such a run does not fail), and says: "Open Claude on your <vault> folder and say: fix my job."
- `/control-tower` can automate a report: it asks what the report should do and where its data comes from, writes the skill in the vault (checked with `check-skill`), offers to try it, asks when it should run, schedules it with `add-job` after showing what it will use, runs it once and hands any refusal to `/job-permissions`, or creates its routine when it runs on claude.ai. "Automate a report" is in the first question; connecting a tool offers to make a report with it.
- A report of your own can run on claude.ai as a cloud routine (`add-job --runs-on cloud`, `"runs_on": "cloud"`): the installer renders it from the same skill-job prompt into `routines/my--<id>.prompt.md` and `routines.json` with its connectors, and schedules nothing on this computer; the routine is created by the user like a pack routine. claude.ai connectors (Gmail) become sources of cloud reports (`add-connection --connector`); a report on this computer cannot use one, and a cloud report cannot use the vault's MCP servers or commands. `uninstall.py` lists the routines to delete on claude.ai. A cloud routine commits only its own report. The runner now refuses to start any job while the vault's `.claude/settings.json` would widen it (rules, hooks, env, MCP servers), and the doctor fails: such a file could come from a synced vault or a routine.
- Schedule any skill of the vault as a report of your own: `configure.py add-job` / `remove-job` record `my_jobs` (`{id: {skill, uses}}`; its days and time in `jobs.<id>`, like any job), and the installer renders it from one generic prompt (`core/jobs/skill-job/prompt.md.tmpl`) that reads the skill with `Read`, takes its dates from the Run context and writes `journal/reports/my-<id>-YYYY-MM-DD.md`. Its sources (`uses`) are known tools and connections; it gets their read tools and nothing else, and a connection's server starts only for the reports that use it. `configure.py check-skill` checks the skill like a pack skill (closed frontmatter, no `allowed-tools`, dates from the Run context); `set --job <id> --uses` changes the sources; a connection a report uses cannot be removed, and a connection id may not be a capability name. The doctor warns when a report's skill is missing. Your reports write `journal/reports/my-<id>-...`, a name no pack report may use. Any change that adds a scheduled run (a report, a pack, a job turned back on) now needs the user's yes like any other new access.
- Connect a tool the kit does not know, by answering questions in `/control-tower`: an MCP address (`configure.py add-server` adds an https address on a public host, with nothing secret in it, to the vault's `.mcp.json` with `claude mcp add`, never a shell) or a command-line tool (its web addresses known or recorded first), with the read tools reports may use (a command's rules end with a read word: `gh pr list`, never the group `gh pr`; an address whose path or subdomain holds a long code is for a developer). `configure.py add-connection` / `remove-connection` record `connections` in the answers (`{id: {server or command, read_tools}}`), every tool checked like a grant; `show` and `choices --kind connections` list them. A connection's server is approved and fingerprinted like a known tool's, and no report uses a connection until it is chosen as a source of one of the user's own reports.
- Connect a known tool by answering questions: `/control-tower` adds it to the vault's `.mcp.json` (the servers scheduled reports can see), has you sign in, records the server name reports really see (`configure.py connect`, `servers` in the answers) so the adapter's rules follow it, and lets you choose the read tools of an adapter that ships none (`configure.py set-permissions`). Each job gets its own `mcp.json` with a copy of the connected servers it calls, and the runner passes it with `--strict-mcp-config`, so a job starts no other server; a server whose `.mcp.json` entry changed since it was connected (a fingerprint) is dropped at the next change of setup and the doctor fails; jobs cannot read `.mcp.json`; the doctor flags `.mcp.json` servers no report is connected to. Adapter install commands add servers to the vault (`--scope project`) and keep keys as quoted `${NAME}` references, never their values; tools set up by a developer (keys, client secrets, Sentry's organization address) are finished with "connect" afterwards. Adapters say how they are connected (`connect`: `sign-in` or `developer`). Connecting a new server, or one whose entry changed, is new access that needs a yes. Jobs write only Markdown notes (the guard), so they cannot plant a file a server or a tool would run; Google Analytics runs with `pipx run --spec` for the same reason. Runtime fact F1c (the `--strict-mcp-config` check) is added to the facts script.
- `configure.py probe` runs Claude once the way a job runs and records the MCP servers and tools a job sees (claude.ai connectors are counted, not offered: jobs cannot use them). `configure.py choices` turns any list into questions of at most 4 options ("All N" / "Let me choose" / "None", then pages of 4), and never offers a tool that acts; every skill asks long lists through it (a test checks it). More MCP tool names count as actions and are never granted (call, invoke, insert, put, patch, save, cancel, drop, navigate, click, fill, draft, destructive, sql, start, stop, push, grant, reset...; commit, start, draft, sql and type are nouns after a read verb, as in get_commit), and `choices` recommends only tools whose name starts with a read verb (get, list, search, query...); the CloudWatch adapter no longer allows `cancel_logs_insight_query`. `probe` starts only the `.mcp.json` servers named with `--server`.
- `/control-tower` in the vault: check the setup, change it (profiles, tools, report times, which reports run, automatic runs), fix a blocked job, get a kit file back, by answering questions. `configure.py set --dry-run` shows what a change would do; `configure.py fresh-copy` restores the kit version of a file and keeps yours in `_system/archive/`. No message or doc tells you to edit the answers file any more (a test checks it).
- `installer/configure.py` (was `installer/permissions.py`) is the one door to `answers.json`: `show` (packs, tools, jobs with days, time and state, schedule) and `set` (`--add-pack`, `--remove-pack`, `--tool cap=tool`, `--job id --time/--days/--enabled`, `--schedule on|off`) join `grant`, `revoke`, `add-command`, `remove-command` and `denials` (was `list`). Every change is checked before anything is written, applied by the installer, and rolled back if the installer refuses; a loaded schedule follows the change. A change that gives jobs more access (a job turned back on, a pack or a tool added) is refused until the user has seen that access and said yes (`--accept-access`). Loading the schedule no longer removes the launchd agents of another install (with other job ids).
- Jobs never use the `Skill` tool (denied, and never granted): a skill could bring its own tools. Job prompts already read their skill file with `Read`.
- A command granted to a job reaches, inside the sandbox, the web addresses it needs: from `adapters/commands.json` (`gh`, `twg`, `slackcli`, measured with the real CLI) and from the `commands` answers, which `/job-permissions` records after asking which address an unknown command talks to (`installer/configure.py add-command`). The `gh` exception for macOS certificates comes from that table. Host names are exact and public, never a wildcard, an IP address or a local-only name, for `WebFetch` too; write folders are a tool's own folder under a per-user log or cache root. `remove-command` takes an address back.
- Jobs no longer run `date` or `ls`: `Bash(date)` and `Bash(ls:*)` leave the base rules, the guard loses its `date` argument parser, and generic file readers (`date`, `ls`, `cat`, `head`, `tail`, `grep`, `rg`, `tar`, `open`...) can never be granted, by a pack or by `/job-permissions`. The next update of the kit refreshes the job settings.
- Jobs get their dates from the runner: a `## Run context` block at the top of each prompt (now, today, ISO weeks, previous working day, in the installed timezone). Job prompts no longer run `date`, `weekly-digest` finds notes with Glob instead of `ls`, and the skills jobs follow say to use the Run context first. See docs/scheduling.md.
- `tests/e2e/smoke_real_claude.py --facts` checks the Claude Code behaviours the kit relies on, with the real CLI; results in docs/design/runtime-facts.md. Found with Claude Code 2.1.332: jobs do not see MCP servers added at user scope (docs/adapters.md now says so), and a claude.ai connector's tool is refused in a job even with its exact allow rule.
- Job permissions, secure by default and granted by answering questions: the installer report lists in plain words what each job may use (`permissions_summary`), the guided installer asks once and disables the jobs you refuse, and the new vault skill `/job-permissions` explains each refusal of a job's latest run (`<ct_home>/logs/<job>.denials.json`) and allows what you say yes to (`job_permissions` in the answers, written by `installer/configure.py`, never by hand). See docs/permissions.md.
- Simpler guard and policy: the guard no longer parses shell commands (which commands a job runs is decided by its rules); one list of things never allowed, for packs and users alike. The `trusted_commands`, `trusted_env`, `trusted_mcp_tools` and `trusted_domains` answers are gone (ignored if present). Re-run the installer (`--update`).
- Claude Code's sandbox around every job that may run a command, automatically: writes only in the vault, no read of the secret folders, network only to the hosts the job and its adapters declare (`network`); the job refuses to run where the sandbox is not available. The `strict` answer is no longer needed and is ignored. On Linux the doctor fails when `bwrap` or `socat` is missing.
- Private packs (`pack_dirs` in the answers): packs kept outside the repository, which may replace or exclude core files (templates, rules, language). See docs/private-packs.md.
- Runtime-only installs (`--runtime-only`): runner, guard, jobs and schedule on an existing vault, nothing written in it but `.control-tower/`.
- `install.py --update`: refresh the kit files you never edited, keep the ones you edited (new version saved in `.control-tower/updates/`), leave deleted files deleted. See docs/updating.md.
- Job guard: jobs can read their skills, adapter notes and rules again (they wrote empty reports); glob and grep bypasses closed. Re-run the installer (`--update`) to get the fixed guard.
